## Схема публикации

1. Редактор сохраняет страницы, каталог, страны, новости и настройки в защищённой CMS на Cloudflare Pages. Новые и изменённые посты Telegram также сохраняются в D1.
2. `GET /api/public/manifest` выдаёт только время формирования и безопасные публичные маршруты из текущей D1. Черновики, скрытые и будущие новости, настройки, счета, сессии и закупочные поля в ответ не входят.
3. Экспортёр получает готовый HTML только перечисленных маршрутов и публичные ресурсы с Pages. Ссылки на снятые с публикации страницы убираются из меню. Пагинация `/news?page=N` становится `/news/page/N/` для GitHub Pages. Приватные страницы админки не выгружаются.
4. Workflow `.github/workflows/publish-site.yml` загружает **только `site/github-dist/`** как Pages-артефакт и публикует его на прежнем `avocado.rest`.
5. Чат работает через существующий Worker, админка — на `avocado-rest.pages.dev/admin`. DNS, `CNAME`, база и история обращений сохраняются.

Workflow запускается после push в `main`, вручную через Actions и по расписанию
`7,22,37,52 * * * *`: четыре раза в час, на 7-й, 22-й, 37-й и 52-й минуте UTC.
GitHub может задерживать плановые запуски. Правки, скрытие и новые материалы
становятся видимыми на основном сайте после следующей успешной публикации.
Ошибочная сборка не должна заменять предыдущий рабочий артефакт.

Дополнительные секреты Cloudflare/GitHub для workflow не используются. Экспорт
читает публичный серверный сайт; публикация использует встроенный токен задания
GitHub и OIDC-разрешение Pages. Токен Cloudflare остаётся в локальном игнорируемом
файле и нужен только для отдельных обновлений backend, схемы D1 и bindings.

## Решения

- Astro 7.3.2 + @astrojs/cloudflare 14.3.1. Адаптер выпускает Workers build; собственный `site/scripts/package-pages.mjs` упаковывает его ES-модули в Cloudflare Pages advanced mode. Совместимость проверена в настоящем workerd. При обновлении адаптера нужно повторить проверки. Старые версии Astro/адаптера не использованы из-за известных уязвимостей.
- В Cloudflare публикуется только `site/pages-dist/`; в GitHub Pages — только `site/github-dist/`. Скрытые файлы и серверный wrangler.json исключаются; сборка блокируется при обнаружении известных секретов. Pages-конфиг вынесен в `pages/`, чтобы избежать автоматической подмены конфигом Workers. Исходники CMS, секреты, локальные данные и закупочные источники не входят в статический экспорт.
- GitHub Pages использует источник `GitHub Actions` (`build_type: workflow`). Корневой `index.html` — исторический лендинг для отката, не источник нового production. `_config.yml` сохраняет исключения для возможного отката к Jekyll.
- Общая D1 avocado-chat сохраняет существующие sessions/messages. CMS использует отдельные таблицы; миграции только добавляют данные/схему.
- Серверное приложение Pages обращается к чату через service binding. Публичный сайт GitHub Pages обращается прямо к существующему Worker; путь `/api/chat/...` и браузерный `sid` сохраняются. Внутренние ответы оператора защищены отдельным секретом.
- По указанию владельца опубликованы ориентировочные цены и география. Все услуги — от Avocado; наличие «по запросу», Bulletproof — «скоро». Закупочные источники хранятся в закрытых полях D1 и локальном gitignored JSON, не в публичной миграции и репозитории. Публичный слой исключает эти поля.
- Кошельки не выдумываются. Счёт фиксирует актив, сеть и адрес на момент создания; оплату и выдачу подтверждает владелец.
- BTCPay Server — отдельный второй этап после выбора VPS и согласования расходов.

## Критерии приёмки

Production-домен на GitHub Pages открывает все новые страницы и корректные 404;
`/admin` ведёт к защищённой CMS, которая сохраняет в D1. Изменения контента и новые
посты канала попадают в очередную публикацию Actions. Приватные данные отсутствуют
в артефакте, чат/бот работают без изменения контракта; мобильные Performance
и Accessibility >=90. Локальные проверки и Pages-просмотр не заменяют проверку
публикации на `avocado.rest`.

## Включение публикации и откат

1. Проверить серверное Astro-приложение и manifest на `avocado-rest.pages.dev`, существующий чат и CMS. В серверной конфигурации установить `PUBLIC_PUBLISH_MODE=github`, чтобы админка показывала срок обновления контента и ссылку на основной сайт.
2. Проверить статический экспорт в `site/github-dist/`: опубликованные страницы, подробные карточки, пагинацию, ресурсы, внешнюю ссылку админки, чат, 404 и отсутствие приватных файлов. Просмотреть 1440/390 и выполнить мобильный Lighthouse.
3. Сохранить существующий `CNAME`. В настройках репозитория Pages выбрать `GitHub Actions` (`build_type: workflow`), затем выполнить `Publish Avocado website`.
4. После успешного Actions deploy проверить `https://avocado.rest` и глубокие ссылки, 404, чат, переход в CMS и Lighthouse. Убедиться, что запланированные публикации включены.
5. Для отката сначала отключить `publish-site.yml`, затем выбрать Pages → `Deploy from a branch`, ветку `main`, корень `/` (`build_type: legacy`). Появится сохранённый лендинг; DNS и `CNAME` остаются прежними, CMS, D1 и чат сохраняются. Для возврата к мини-сайту включить workflow, вернуть источник `GitHub Actions` и запустить успешную публикацию.

Изменения кода Astro сначала выкладываются в Cloudflare Pages; экспорт берёт
отрендеренный HTML оттуда. Правки только в CMS отдельного backend deploy не требуют.

## BTCPay, второй этап

После подтверждения VPS, домена, поддерживаемых монет и бюджета: отдельный BTCPay,
резервные копии и обновления, проверяемые webhook для счетов, повторная доставка
без дублей, ручное разрешение исключений. До этого действует только ручное
подтверждение владельцем; внешних платёжных процессоров нет.
