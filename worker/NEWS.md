# Новости Telegram и ответ из админки

Текущий чат `/api/chat/:sid/messages` и маршрутизация ответов бота сохранены.
Воркер получает только разрешённый канал; сообщения каналов не попадают в чаты.

## Подключение после получения данных владельца

1. Добавить @avogurubot администратором канала.
2. Задать `NEWS_CHANNEL_ID` как числовой id канала (`-100…`) или `@username`.
   Пустое значение полностью выключает импорт. Числовой id сохраняет привязку при
   смене username. Ссылки вида `https://t.me/...` не принимаются.
3. Подключить приватный R2 bucket к Worker и Pages под одним binding `NEWS_MEDIA`.
   D1 binding `DB` у обоих должен указывать на общую `avocado-chat`.
4. Применить `worker/migrations/0002_news.sql` к общей D1. Воркер также создаёт
   таблицу лениво через `ensureNewsSchema` — это совместимо с миграцией.
5. После деплоя один раз вызвать `/tg/setup` с `X-Setup-Key: <WEBHOOK_SECRET>`.
   `setWebhook` включает `message`, `channel_post`, `edited_channel_post` и сохраняет
   очередь (`drop_pending_updates: false`). Токен и секрет не помещать в URL.

Пример дополнений к конфигурации (значения bucket и канала задаёт владелец):

```toml
[vars]
NEWS_CHANNEL_ID = ""

[[r2_buckets]]
binding = "NEWS_MEDIA"
bucket_name = "<shared-news-media-bucket>"
```

Существующую секцию `[vars]` нужно дополнить, а не продублировать.
Секрет `ADMIN_API_SECRET` (случайный, минимум 32 символа) задаётся одинаково
в Worker и Pages. В браузер он не передаётся. Работающий `WEBHOOK_SECRET` сохраняется.

## Контент и фотографии

DDL находится в [migrations/0002_news.sql](migrations/0002_news.sql); тот же DDL
экспортирован как `NEWS_SCHEMA` из [src/news.js](src/news.js).

- Все даты — Unix milliseconds. `source_chat_id` — строка, `source_message_id` — число.
- Текст, первая строка-заголовок и краткое описание хранятся как **plain text**.
  Страница выводит их с HTML-экранированием; Telegram HTML/entities не исполняются.
- Новые записи видимы (`hidden=0`), не закреплены (`pinned=0`). Пара channel/message
  уникальна. Повтор webhook не создаёт второй пост; старый update не откатывает новый.
- Правки Telegram сохраняют скрытие и закрепление. После ручной правки админка
  устанавливает `manual_override=1`: импорт сохраняет title/body/excerpt/media,
  продолжая обновлять источник. Для возобновления синхронизации снять этот флаг.
- Импортируется наибольшее фото `message.photo`, максимум 8 MiB. Разрешены JPEG,
  PNG и WebP по сигнатуре байтов. URL из постов, документы и SVG не скачиваются.
- R2 key: `news/telegram/<channel>/<message>/<content-hash>.<ext>`, без bot token.
  Сайт отдаёт `/media/<key>` через свой защищённый правилами публикации обработчик.
  Telegram download URL в D1 и логах не сохраняется.
- Без R2 binding сохраняются текст и Telegram `media_file_id`; `media_key` остаётся
  пустым. После включения R2 и деплоя binding `NEWS_MEDIA` существующий cron раз в
  15 минут сам догружает до 10 ожидающих фото за запуск. Повторять исходный пост
  или ждать его редактирования не нужно. Архив канала Bot API не отдаёт.
- Backfill не меняет текст, даты, скрытие или закрепление; ручные правки
  (`manual_override=1`) пропускает. Условное обновление защищает от одновременной
  замены фото в Telegram или админке. Временные сбои остаются в очереди; выборка
  случайная, чтобы один недоступный файл не задерживал остальные. Фото слишком
  большого размера, неверного формата или с отклонённым Telegram `file_id`
  исключается из очереди очисткой `media_file_id`. Бот не отправляет сообщений
  при догрузке. Экспорт `backfillNewsMedia(env, telegramApi, limit=10)` доступен
  для серверного запуска; лимит ограничен 10 независимо от переданного значения.
- При временном сбое D1, Telegram download или R2 воркер отвечает `503`, чтобы
  Telegram повторил импорт. Недопустимое фото пропускается, текст публикуется.
- В текущей версии каждый message из альбома — отдельная новость. Видео и другие
  вложения не копируются. Удаление исходного поста Telegram не сообщает боту:
  скрыть такую новость нужно в админке. Неиспользуемые фото после замены остаются
  в R2 до отдельной очистки.

## Server-to-server ответ из админки

Pages читает `sessions`/`messages` непосредственно из общей D1. Для отправки:

```http
POST /api/internal/chat/<sid>/reply
X-Admin-Api-Key: <ADMIN_API_SECRET>
Content-Type: application/json

{"text":"Ответ посетителю"}
```

Вызов выполняет только сервер Pages, желательно через service binding `CHAT_SERVICE`.
Тело — непустая строка до 4096 символов; авторизация сравнивает SHA-256 секретов
за фиксированное число операций. Внутренние маршруты не возвращают CORS-заголовки.

Успех: `{"id":123,"ts":1789000000000,"delivered":true,"channel":"website"}`.
Ответ сохраняется в D1 с `sender=admin`, обновляет `last_admin_at` и доступен виджету.
Если `tg_user_chat_id` заполнен, бот отправляет текст посетителю и `channel=telegram`.
Если Telegram отклонил отправку, ответ остаётся в D1 и API возвращает `delivered=false`.
Админка сообщает это оператору и не повторяет запрос автоматически.

Ошибки: `403` — неверный/отсутствующий секрет; `400` — неверный sid/текст;
`404` — нет диалога; `405` — метод не POST. Секрет короче 32 символов выключает API.
