# Мини-сайт Avocado

Astro 7.3.2 + `@astrojs/cloudflare` 14.3.1. Домен `avocado.rest` остаётся
на GitHub Pages. Cloudflare Pages
`avocado-rest.pages.dev` рендерит HTML из текущей D1 и обслуживает защищённую CMS.
GitHub Actions экспортирует публичные страницы и ресурсы в статический артефакт
и публикует его на основном домене. **51 публичная страница уже доступна на `https://avocado.rest`.**

D1 `avocado-chat` общая с ботом: существующие `sessions/messages` сохраняются,
CMS добавляет собственные таблицы. Чат основного сайта обращается напрямую
к прежнему Cloudflare Worker; контракт `/api/chat/...` и браузерный `sid` сохранены.
R2 `avocado-media` предназначен для загрузок и фото новостей. Если R2 ещё не включён,
текстовый контент и готовые изображения сайта работают; это не препятствует публикации.

## Страницы и CMS

Главная начинается с хостинга: направления с ценами, подбор домена, четыре
тарифа VPS, страны и собственное ПО Hass/Ettinger. Полный каталог сравнивает
конфигурации по CPU, RAM, диску и порту. Фильтры страны, RAM и валюты работают
на статике; состояние хранится в hash, например `/catalog/vps/#country=FI`.
Флаги — локальные SVG; география VPS отделена от географии прокси.

«Заказать» открывает окно с выбранным тарифом и страной. После уточнения ОС
и комментария заявка добавляется к существующему черновику чата; автоматической
отправки нет. Подбор домена проверяет синтаксис имени и показывает цену зоны.
Доступность, итоговую сумму и срок выдачи подтверждает оператор до оплаты.
Внешние API наличия, регистрации и платежей не подключены.

Миграция `0006` меняет только нетронутые исходные тексты пяти публичных страниц.
Редакторские правки, цены, статусы, кошельки и настройки сохраняются.

Главная, `/software` (разработка ПО), `/hass`, `/ettinger`, `/rent`, `/catalog` и пять категорий,
`/countries`, `/payment`, `/news`, `/contacts`. Каталог поддерживает детальные
страницы услуг. Дополнительные страницы и новости получают собственные адреса.
Новости имеют пагинацию; скрытые и будущие публикации не попадают в экспорт.
На Pages используется `/news?page=2`, на GitHub Pages — `/news/page/2/`.
Публичный сайт отражает состояние на момент последней успешной публикации:
новые материалы, правки и скрытие вступают в силу после обновления артефакта.

`https://avocado.rest/admin` переводит в `https://avocado-rest.pages.dev/admin`.
Там доступны страницы, услуги, страны, новости, чаты, счета и настройки.
Контент — простой текст с абзацами, HTML не исполняется. Цены, страны, наличие,
контакты, кошельки и согласованные условия редактируются через формы.
Реквизиты по умолчанию пустые, Bulletproof — «скоро». Миграции `0004`/`0005`
добавляют период цены, примечание, официальный источник и дату проверки,
31 предварительное предложение партнёров и 17 стран. Цены сохраняют исходную
валюту и единицу тарификации; наличие подтверждает оператор. Часть доменных цен
взята из демонстрационной витрины и используется только как ориентир. Посетитель видит
услуги Avocado: названия, ссылки, закупочные источники и примечания о поставщиках
не публикуются. `source_*` доступны только в админке; публичный `getSiteData`
исключает их из результата. Интеграции партнёров не подключены.
Миграция не перезаписывает существующие редакторские записи и настройки.
Закупочные источники и исследование хранятся только локально в игнорируемой
папке `output/partner-research/`; привязки к товарам — `output/procurement-sources.json`.
После миграций `node scripts/import-procurement.mjs` переносит привязки в закрытые
поля D1, сохраняя уже заполненные администратором источники. Файл с привязками,
результаты исследования и имена поставщиков не публикуются в Git.

Позиционирование, логотип и персонаж: [MASTER.md](../design-system/avocado/MASTER.md)
и [brand-art-direction.md](../design-system/avocado/brand-art-direction.md).

Админка использует PBKDF2 и сессии D1 на 8 часов: HttpOnly/Secure/SameSite cookie,
CSRF, проверку Origin, ограничение попыток входа, журнал изменений и `no-store`.
Без настроенного пароля и базы вход закрыт. Встроенные Astro sessions отключены.
Ответ из админки идёт в существующую историю виджета или посетителю в Telegram.
Внутренний endpoint воркера требует отдельный `ADMIN_API_SECRET`.

## Локальный запуск (PowerShell)

Проверено на установленном на сервере Node 26 и npm. Из `site/`:

```powershell
npm ci
node scripts/local-setup.mjs
npm run build
```

Локальный пароль записывается в игнорируемый `site/output/local-access.json`.
Продакшен использует другие секреты. Для полного окружения запустите локальный
Telegram mock из `worker/` командой `npm run mock:tg`, затем в `site/`:

```powershell
npm run dev:stack
```

Сайт: `http://127.0.0.1:4322`, админка: `/admin`, тестовый чат: порт 4331.
Миграции применяются автоматически в отдельную D1. Оба приложения работают
в одном workerd, поэтому записи в общую локальную базу не конфликтуют.
Тестовые сообщения остаются в локальном mock, рабочий бот не вызывается.
После сборки перезапустите `dev:stack`. Windows: завершайте родительский Node
вместе с дочерними процессами; отдельное завершение workerd блокирует состояние.

`npm run dev` удобен для вёрстки. `npm run preview` запускает упакованный Pages
на 4321; для чата ему требуется отдельно настроенный локальный service binding.
Полные проверки выполняйте в `dev:stack`.

Проверка заказа: `node tests/order-ui.cjs` с `UI_BASE_URL`. Проверка фильтров:
`node tests/catalog-ui.cjs http://127.0.0.1:4322`. Оба сценария проверяют 1440/390;
чат в тесте заказа перехвачен, рабочий бот не получает сообщения. Перед
публикацией также выполняются `npm test`, `npm run check`, сборка, статический
экспорт, `site-ui.cjs` и мобильный Lighthouse.

нагрузочные проверки параллельно с Lighthouse.

## Сборка серверного приложения для Cloudflare Pages

Новый адаптер Astro ориентирован на Workers. `scripts/package-pages.mjs`
упаковывает его серверные ES-модули в Pages advanced mode (`_worker.js/index.js`)
и переносит клиентскую статику с `_routes.json`. Это собственный слой совместимости,
проверяемый сборкой и тестами в workerd; при обновлении адаптера проверяйте его заново.
Конфигурация сборки — `wrangler.build.jsonc`, Pages — `../pages/wrangler.toml`.
Pages-конфиг вынесен наружу, чтобы Wrangler не подменял его конфигурацией Workers
из автоматически созданного `.wrangler/deploy/config.json`.

Основание упаковки: [Cloudflare Pages advanced mode](https://developers.cloudflare.com/pages/functions/advanced-mode/).
Ограничения и изменения адаптера: [Astro Cloudflare](https://docs.astro.build/en/guides/integrations-guide/cloudflare/).

Скрытые файлы, `.dev.vars` и серверный `wrangler.json` не входят в пакет.
Каждая сборка сканируется на известные секреты. В Cloudflare публикуется **только `pages-dist/`**,
а не `dist/`, в котором адаптер может создать копию локальных переменных.

## Публикация основного сайта на GitHub Pages

Workflow [`../.github/workflows/publish-site.yml`](../.github/workflows/publish-site.yml)
запускается после push в `main`, вручную через Actions и по расписанию
`7,22,37,52 * * * *` (UTC, четыре раза в час). Плановое время не гарантирует
мгновенный старт: GitHub может задержать запуск. Админка при
`PUBLIC_PUBLISH_MODE=github` показывает это правило в разделах контента.

Экспортёр получает с Pages `GET /api/public/manifest`: только `generatedAt`
и отсортированный список публичных маршрутов. Список строится из опубликованных
страниц и услуг, видимых новостей с наступившей датой публикации и их пагинации.
Служебные маршруты, черновики, скрытые и будущие новости исключены. Ответ
не содержит текстов записей, закупочных полей, настроек, счетов или сессий.
Endpoint работает без авторизации, с `no-store` и `noindex`.

По этому списку экспортёр получает готовый публичный HTML и нужные изображения,
шрифты и скрипты, преобразует пагинацию и создаёт **`site/github-dist/`**.
Исходники репозитория, серверные модули, `.dev.vars`, локальные базы, резервные копии,
закупочные источники и документация в публикуемый артефакт не копируются.
Переход `/admin` ведёт в защищённую CMS на Pages; её HTML не экспортируется.

Workflow использует встроенный токен задания GitHub и OIDC с ограниченными
правами публикации Pages. Отдельные токены Cloudflare/GitHub в Actions Secrets
не нужны. Доступ к DNS и включение R2 не требуются. `CNAME` сохраняет `avocado.rest`.
Источник GitHub Pages — `GitHub Actions` (`build_type: workflow`), поэтому
корневой `index.html` остаётся историческим резервом, а не production-шаблоном.

Правки контента в D1 подхватываются следующим успешным запуском, включая новые
посты канала. При изменении Astro-шаблонов сначала соберите и выложите серверное
приложение на Cloudflare Pages по инструкции ниже, затем запустите workflow.
Локальный экспорт после установки зависимостей: `npm run export:github` из `site/`.
Просмотр артефакта: `node scripts/preview-github.mjs` (порт 8000).
Проверка ссылок, ресурсов, приватных путей и конфигурации чата:
`node scripts/github-smoke.mjs`; для production добавьте `--base https://avocado.rest`.
Откат к сохранённому лендингу: отключить workflow и выбрать в настройках Pages
`Deploy from a branch`, `main`, `/` (`build_type: legacy`). DNS, `CNAME` и D1
при этом сохраняются. Подробности — [MIGRATION.md](../design-system/avocado/MIGRATION.md).

## Выкладка серверного приложения и CMS

В игнорируемом `worker/.dev.vars.prod` должен быть `CLOUDFLARE_API_TOKEN`
с доступом к Workers, Pages и D1; для подключения R2 нужны соответствующие права.
Разрешения DNS для принятой схемы размещения не нужны.
OAuth с этого сервера не используется. Не вставляйте значения в команды или Git.

Из `site/`, после успешных локальных проверок:

```powershell
node scripts/cloudflare-release.mjs prepare
node scripts/cloudflare-release.mjs migrate
node scripts/cloudflare-release.mjs worker
node scripts/cloudflare-release.mjs webhook
node scripts/cloudflare-release.mjs site
```

`prepare` создаёт проект `avocado-rest`, bindings и случайные секреты; пароль
сохраняет в `site/output/production-access.json` (открывайте локально).
`migrate` сначала экспортирует удалённую D1 в `site/output/backups/`, затем
добавляет таблицы и исходный контент. `worker` сохраняет старые секреты и включает
`@avocadodev`; `webhook` добавляет channel_post/edited_channel_post без сброса очереди.
`site` ещё раз проверяет пакет и выкладывает его на `avocado-rest.pages.dev`.
После выкладки: `node scripts/production-smoke.mjs --admin` проверяет страницы,
защиту и вход с локальным паролем, читает историю чата и настройки webhook.
Контент, сообщения, счета и канал этот smoke-тест не изменяет.

Если R2 ещё не включён в аккаунте, серверное приложение работает без загрузки файлов.
Текст новостей сохраняется, фото ожидают включения R2. После активации повторите
`prepare`, `worker`, `site`; cron догрузит фотографии. Проверьте SSR, вход,
контент и здоровье чата на Pages, затем опубликуйте новый статический экспорт.
Переключение DNS не выполняется.

## Криптовалютные счета

В настройках добавьте подтверждённый адрес и сеть. При создании счёта фиксируются
точная десятичная сумма и снимок реквизитов; последующие изменения кошелька их
не меняют. Оператор передаёт реквизиты посетителю, проверяет перевод вручную,
вводит идентификатор транзакции и отмечает оплату, затем выдачу. Только ожидающий
счёт можно отменить. Никакие процессоры или блокчейн-запросы не подключены.

Условия оплаты и возврата публикуйте после утверждения владельцем. BTCPay Server —
следующий этап: отдельный VPS, домен и резервные копии; выбор ресурсов и расходы
требуют данных владельца. Текущая система не выдаёт ручную проверку за автоматическую.

## Изображения

Пять промптов категорий — в `../design-system/avocado/render-brief.md` и
игнорируемой папке `../assets/renders/`. Оригиналы готовит владелец во внешнем ИИ.
`python scripts/convert-renders.py` создаёт WebP и мобильные варианты, когда
исходники появятся; `npm run assets` переносит одобренные файлы в public.
`scripts/build-og.cjs` создаёт OG с прозрачным авокадо; исходный PNG остаётся
в `assets/og-minisite.png`. Публичный сайт использует локальные шрифты и WebP srcset.
